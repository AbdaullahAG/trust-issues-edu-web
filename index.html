Open ≠ free ≠ safe

Three myths, one minute each. Click a card.

Myth 1: “Open source is free”

The code is free to read and use. The work is not free. OpenSSL protected banks and email on about $2,000 a year in donations when Heartbleed hit (2014). Maintainers pay with time and energy, and you can fund them (GitHub Sponsors, Open Collective).

Myth 2: “Open means no rules”

A license is a contract. MIT and Apache are permissive. GPL may require you to open your own code if you distribute a product built on it (not legal advice). Two in three audited codebases had license conflicts (OSSRA 2026).

Myth 3: “Many eyes make it safe”

Only if eyes are actually looking. Heartbleed's code was public too. Open means auditable, not audited. Supply chain failures are now A03 in the OWASP Top 10:2025.

Open means you can inspect it. It doesn't mean someone did.

How Git thinks

Git is a distributed version control system. It does not record every keystroke or save: it stores snapshots when you make a commit. GitHub is a platform that hosts Git repositories and adds Pull Requests, code review and CI/CD.

Try the three-stage workflow: edit, then run each command in order.

Why staging matters

You edited three files but want to commit one. Staging lets you choose exactly what goes in, so you don't ship changes you never meant to share.

What Git records

Author name and email, time, and the commit message. You set the name and email yourself, so they are metadata, not proof of who made the change. That is why commit signing exists.

fetch downloads remote changes without touching your branch, so you can inspect first. pull fetches and then merges or rebases. With code you don't fully trust, look before you merge.

Delete is not undo


Find the secret before this commit. Click the line.


$ git add . && git commit -m "add config" && git push
$ git rm config.env && git commit -m "remove config" && git push   # secret is still in the previous commit
$ git reset --hard HEAD~1 && git push --force   # moves the branch pointer, rewrites published history


The old commit can remain in clones, forks, Pull Requests and cached views. Rewriting history does not guarantee every copy is gone.
The Secret Leak Rule: a leaked secret is a compromised secret.
1 Revoke it · 2 Rotate: issue a new one · 3 Check how it was used · 4 Clean history if needed (it never replaces revoking) · 5 Turn on prevention (push protection, secret scanning).


.gitignore is not enough
It ignores untracked files only. For a file Git already tracks: git rm --cached .env, which removes it from the index, not from past commits. Typical entries: .env  .env.*  !.env.example  *.pem  *.key  secrets/



Who are you? What may you do?


Authentication proves who you are. Authorization decides what you may do. Click each control.


MFA / passkeys
Protect the account itself. The keyv and axios attacks started with a maintainer account.


SSH keys
Authenticate Git connections over SSH. Protect the private key.


Fine-grained personal access tokens
Scope a token to specific repositories and permissions. GitHub recommends them over classic tokens where suitable.


Least privilege + token expiry
Grant the minimum, for the shortest time. Limit what a stolen credential can do.


user.name / user.email
Commit metadata, not a login. They do not authenticate you to GitHub and prove nothing about who you are.


Commit signing
Shows a commit was signed with a particular key and not altered.


Signed ≠ secure. A signature doesn't prove the code is safe, that its author wasn't tricked, or that the key wasn't stolen. Verified provenance proves where an artifact was built, not that the source is clean.

Three attacks, three lessons


xz Utils (2024): trust. Over about two years, “Jia Tan” earned maintainer rights on a tired maintainer's project and hid a backdoor in binary test files and the build process. Found by chance, via a 500 ms SSH delay. Lesson: old reputation doesn't make a new change safe.


keyv / ChainDrop (Aug 2026): history and provenance. A hijacked maintainer account added a malicious install script; a worm spread to 400+ packages. The release carried genuine build provenance, yet it was built from malicious source. Lesson: provenance links an artifact to a build, not to safe code.


axios (Mar 2026): account and publishing. Two malicious versions were published from a hijacked maintainer session, outside the trusted CI path, and stayed live about three hours. Lesson: protect accounts, use trusted publishing, spread permissions.


Sources: Datadog Security Labs, Wiz, Aikido, TechRepublic. See Sources.



Understand Git. Control your changes. Protect your supply chain.


Before commit review what you staged. Before push know what you are sharing. Before merge review everything, not only the visible code.


If you leak a secret: revoke and rotate first.


If you maintain a project: don't depend on one person or account. Enable protection and review.


Every commit tells a story, but not every commit deserves your trust.
